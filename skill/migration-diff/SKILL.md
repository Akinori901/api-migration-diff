# 移行差分比較スキル

旧システムと新システムの同一エンドポイントについて、
ロジック・レスポンス構造・バリデーションの差分を比較し、レポートを出力する。

**このスキルが答える問い**: 「移植したものは、本当に同じように動くのか」

移行作業には3つの段階があり、このスキルは**最後の検品**を担当する。

| 段階 | 問い |
|---|---|
| 棚卸し | 何がまだ移植されていないか |
| 移植 | 移植する |
| **検証（このスキル）** | **移植したものは正しいか** |

## 前提

プロジェクトのルートの `migration.config.yml` に旧・新システムの構成を書いておく
（[api-migration-diff](https://github.com/Akinori901/api-migration-diff) の `examples/migration.config.yml` を参照）。
**設定ファイルが無ければ、推測で進めずに作成を促して止まる。**

```yaml
legacy:
  name: legacy-monolith
  path: ./legacy-monolith
  routes: routes/api.php        # ルート定義の在り処
services:
  - name: auth-service
    path: ./auth-service
    routes: routes/api.php
  - name: main-service
    path: ./main-service
    routes: routes/api.php
output_dir: docs/diff-reports
```

## 手順

### 1. 対象の特定

引数で指定されたエンドポイントを、両システムのルート定義から探す。

```bash
# 旧システム側
grep -n "{対象パス}" {legacy.path}/{legacy.routes}

# 新システム側（全サービス横断）
grep -rn "{対象パス}" {各 services[].path}/{routes}
```

ルート定義の形式はフレームワークによって異なる。設定の `routes` を起点に、
そこから Controller までを辿る。

### 2. ソースコード比較

両方のコードを読み比べ、次の観点で差分を洗い出す。

#### Controller 比較

| 比較項目 | 旧 | 新 | 差分 |
|---------|---|---|------|
| メソッド名 | | | |
| リクエストパラメータ | | | |
| バリデーションルール | | | |
| ビジネスロジック | | | |
| DB操作 | | | |
| レスポンス構造 | | | |

#### バリデーション比較

| フィールド | 旧ルール | 新ルール | 差分 |
|-----------|---------|---------|------|

#### レスポンス構造比較

旧・新それぞれの実際のレスポンス例（JSON）を並べ、**フィールド単位**で突き合わせる。
フィールド数の増減は必ず数える（「62フィールド → 25フィールド、37欠損」のように）。

### 3. 差分の分類

検出した差分を必ず次の4つに分類する。**分類しないまま列挙しない。**

| 分類 | 意味 | 対応 |
|---|---|---|
| **意図的変更** | FW移行等に伴う正当な変更（ミドルウェア、名前空間等） | 対応不要 |
| **改善** | 新側で良くなった点（バリデーション追加、エラーハンドリング強化） | 対応不要 |
| **要修正** | 意図せず変わった箇所（レスポンスキー名の変更、ロジック欠落） | **要対応** |
| **要確認** | 判断が必要な差分 | 人間の判断待ち |

この分類が肝心で、**差分をただ列挙すると「多すぎて読まれない」レポートになる**。
対応が要るものと要らないものを分けて初めて、次のアクションが決まる。

### 4. レポート出力

`{output_dir}/{yyyymmdd}/{対象}.md` に出力する。

テンプレートは、このスキルのディレクトリにある `templates/diff-report.md` を使う。

## 判断基準

- **レスポンス構造の差分を最優先で確認する。**
  フロントエンドの互換性に直結するため、ここが壊れていると画面が動かない。
  ロジックの細かな差異より、まずフィールドの欠損を潰す。
- **フィールドの欠損は必ず定量化する。**
  「一部欠損」ではなく「62 → 25（37欠損・60%）」と書く。
  規模が分からないと優先度が判断できない。
- **欠損のうち「フロントが実際に使っているもの」を区別する。**
  未使用フィールドの欠損は緊急ではない。使用中のものは即修正対象。

## 注意事項

- **コードの修正は行わない**（レポート出力のみ）。
  検証と修正を同じ工程でやると、「直したから大丈夫」で検証が甘くなる。
- **旧システムが実行不可でも成立する。**
  コード読み取りのみで比較する前提のため、環境が失われた旧システムでも検証できる。
  移行案件では「旧環境はもう動かせない」ことが珍しくない。
